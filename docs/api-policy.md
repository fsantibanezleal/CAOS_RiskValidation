# The public API and its policy

From 1.0.0 `riskvalidation` follows semantic versioning, and the public API below is what that promise covers. The
page is tested: `tests/test_public_api.py` fails when a public module has no `__all__` of its own, when the page and the
code disagree on the names of a module in either direction, when a listed name cannot be imported or has no
docstring, when a public module is missing from the page, and when `from riskvalidation.<module> import *` imports
anything but `__all__`. `tests/test_api_surface.py` fails when a name of the 0.9.0 surface disappears or changes its
signature (the one exception is the BL-082 move recorded in the CHANGELOG). The listing is generated by
`python scripts/make_api_policy.py` from the `__all__` lists.

## What the public API is

The public API of 1.0 is the **union of the `__all__` lists**: the top-level list, the list of every subpackage and
the list of every public module. Each module carries its own `__all__`, and that list is its public surface; a
module is public when its name does not start with an underscore. A name listed here is stated by an engine API
contract (`engine-<subpackage>-api`) or by this page, and nothing else is promised: a name that is importable but is
not in a module's `__all__` is not public, whatever it is called.

- A name that is a module is public by path: `from riskvalidation.liquidity import runoff`.
- A **module `__all__`** lists the module's own functions and classes and the constants the contract states.
- A name re-exported by a package (the names of `generators`, `harness`, `regulatory.irb` and the top level) is
  public under the package and under the module that defines it.
- The documented fields of the result records and the policy file format (`TestResult`, `Policy`, the keys of a
  packaged policy file, and the rule names of `riskvalidation.policies.rules`, which a packaged file names) are
  public and are versioned as below.

The package ships `py.typed` (PEP 561): the annotations of the public API are part of it. Widening an annotation (a
wrong `Sequence` where an array is accepted) is a patch; narrowing one, or changing a parameter's name, order or
default, is a signature change.

## Semantic versioning

The version is `MAJOR.MINOR.PATCH`.

- A **patch** release fixes a defect and changes no public name, signature, result field or documented behaviour
  beyond the defect. Correcting a number to what the cited source states is a defect fix: the CHANGELOG gives the old and
  the new value.
- A **minor** release adds: a name, a function, a keyword argument with a default, a field of a result, a test of the
  catalogue, a reason code. It deprecates, it never removes.
- A **major** release may remove a deprecated name, change a signature, or change a documented convention on purpose (a
  different formula, threshold or definition than the one documented). The CHANGELOG states every such change under its
  own heading, and the engine API contract of the subpackage takes a major version in step.

## Deprecation

A public name is never removed in the release that announces it. The rule:

1. A minor release deprecates the name. It keeps working and emits a `DeprecationWarning` that names the version that
   deprecated it, the major that removes it and the replacement. The helpers are in `riskvalidation.core.deprecation`:
   `deprecated(since, removal, use)` for a function or a class, `deprecated_parameter(name, since, removal, use)` for a
   keyword argument that is renamed, and `module_getattr(module_name, aliases)` for a module-level name (a constant, a
   moved function, a module), used as the module's `__getattr__`. Each refuses a `removal` that is not a later major
   `X.0.0`.
2. The name stays through at least one minor release: the removal is in a later major than the one that deprecated it.
3. The documentation page of the name and the CHANGELOG carry the deprecation from the day it lands.

Nothing is deprecated in 1.0.0. The one signature change before the freeze, the move of `p_enter_stress` and
`p_exit_stress` from `DepositorSegment` to `DepositorConfig` (the liquidity depositor generator), is recorded in the
CHANGELOG and in the liquidity API contract.

## Reason codes of the governance functions

The governance functions `scope_test`, `assign_variant`, `anchor_from_test_row`, `rwea_share_of_anchor` and `resolve_policy`
return a reason as an English string, and that return value is unchanged. The **stable key of a reason is its code**
(`"anchor.no_cited_row"`, `"policy.no_threshold"`): codes are public API, and the English sentence is human text that a
minor release may reword. `riskvalidation.governance.reasons` holds the code table with the English and the Spanish
(RAE orthography) of each; `bilingual(code, **values)` gives `{"en": ..., "es": ...}`, and, as a convenience,
`bilingual(sentence)` and `code_of(sentence)` accept the sentence a function returned. A reason with no code raises
`ValueError`. Adding a code is a minor change; removing or renaming a code is a major one.

## Internal helpers

Some modules hold helpers that a contract once named but that are for the engine's own use: the argument checks of
`riskvalidation.liquidity._checks` (`check_nonnegative_stock`, `check_unit_share`, `check_weights_sum_to_one`,
`check_increasing_grid`) are **internal**, no product calls them, and they may change in a minor release.
`riskvalidation.generators` exports `jsonable` and `bvn_equal` as 0.9.0 did; they stay public and may be deprecated in a
minor release.
