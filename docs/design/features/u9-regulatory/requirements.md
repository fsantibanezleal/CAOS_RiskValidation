# U9 regulatory calculators: CRE20 standardised weights, the output floor, SA-CCR, BA-CVA, FRTB SBM with GIRR and the liquidity-horizon cascade (U9-E1)

Sources: research dossier 01 of the Contraste initiative (Basel Pillar 1 and Pillar 2: sections C and C.1 for CRE20 and the output
floor, D.2 for the sensitivities-based method, D.3 for the liquidity-horizon cascade, E.1 for BA-CVA, E.2 for SA-CCR, M.1 and M.3
for the invariants and the acceptance gates), the U9 research addendum R7 (the GIRR parameters, MAR21.42 to MAR21.50) and R8
(BA-CVA has no verified numeric example), and the engine API contract `engine-regulatory-api` 1.0.0 (Contraste
`docs/contracts/engine/regulatory-api.md` with the fixture `docs/contracts/fixtures/regulatory/calculators-fixture.json`, branch
`task/u9-s` at b9543e9 after its Opus review's fix round), whose functions, units, invariants and golden values this unit implements
one by one. Transcribed into `docs/regulatory/u9/`.

EARS (Mavin et al., RE'09, doi:10.1109/RE.2009.9). Every requirement names the gate that fails when it is violated. The engine
computes and states no compliance claim. Every parameter a function returns carries its paragraph, its table and the in-force date
of the chapter version (dossier 01 M.3 item 8). A key outside a table is refused with `ValueError` naming the table and the
paragraph; a missing or invalid input is refused with the field named; the engine never returns a placeholder weight. The five
CRE99 netting sets are reproduced from their trade inputs (transcribed from the BIS page into the fixture) with every intermediate
carried unrounded (CRE99.20), and `round(ead)` equals the published integer exactly. The golden values are reproduced by tests that
recompute them from the trades or from the formula, never by a test that only types the answer.
