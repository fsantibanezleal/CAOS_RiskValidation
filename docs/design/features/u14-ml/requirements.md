# U14-E1 ML validation: robustness, seeds, explanations, effects, generalisation, conformal, leakage, data quality, CBPE, challenger, planted defects and the `ml.` validation tests

Sources: research dossier 06 of the Contraste initiative (model risk management and validation; C.7 ML and AI validation l.979-1058,
I.1 the validation engine catalogue l.1184-1200, I.6 what not to claim), dossier 04 (credit risk models; J.2 l.881-883, ladder P4
l.968), dossier 07 (D patterns 3 and 6) and the ML API contract `engine-ml-api` 1.0.0 (Contraste `docs/contracts/engine/ml-api.md`,
branch `task/u14-s`, reviewed by Opus and fixed on 2026-10-19), whose functions, units, invariants and checks this unit implements
one by one. Transcribed into `docs/ml/`.

EARS (Mavin et al., RE'09, doi:10.1109/RE.2009.9). Every requirement names the gate that fails when it is violated. The engine
computes and states no compliance claim. Tolerances, grids, counts and cut points are conventions, never regulatory thresholds (06
I.6 l.1268-1270). The dossiers print no worked example with numbers for these tests, so no golden value is claimed from them: each
check is an identity, an independent reference (scipy, numpy, hand-computed rows, MAPIE) or a size and power run on a planted
defect, never a test that only types the answer. A light read from a rule stated as "exceeds" keeps a value equal to the cut in the
better colour (the contract's `math.nextafter` rule).
